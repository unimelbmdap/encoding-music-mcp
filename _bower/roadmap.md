# Bower Roadmap

Deferred framework improvements and the triggers that make each one worth picking up. This file is not loaded into context by default — it's a canonical home for ideas that are named but not scheduled.

Each item has a one-line description and a *revisit trigger*: the signal that turns it from deferred to worth doing.

## Deferred items

- **Ethics protocols and the other external obligations of research software have no home, and they constrain design** — *Raised at v0.34 from the framework's own premise. Bower is a research software engineering framework; the defining feature of RSE is that system design must conform to a contract the project did not write and cannot amend.* An approved ethics protocol says where participant data may be stored, who may see it, what must be de-identified before analysis, what happens at the end of the study. A data management plan, an institutional data-classification policy, a funder's open-access condition, an indigenous data-sovereignty commitment and a licence obligation are the same shape. These are **constraints on implementation**, and today they land nowhere: an agent building a feature that writes participant audio to a bucket has no way to know the protocol forbids it.

  **Nothing in the existing model fits, and the misfit is structural rather than a naming problem.** `constitution.md` is normative but *self-authored and freely amendable* — the project decides its own rules, which is exactly what is not true here. An ADR records a decision *the project made*; an obligation is a premise the project's decisions respond to, and filing one as an ADR mislabels a received constraint as a choice. `docs/reference/` is read-only but *not binding* — consulted, not obeyed. `problem-space.md` is narrative and human-owned. The class Bower lacks is **read-only and binding**: externally owned, externally amended, arriving on someone else's schedule.

  **It also inverts the framework's central epistemic rule.** *Code is truth, ADR is hypothesis* holds because a decision can go stale against what was built. Against an approved protocol the direction reverses: the protocol is truth and contradicting code is a **defect**, not evidence the protocol has drifted. This is the first principled exception to that rule, which is a reason to design it deliberately rather than let it accrete — an agent that applies the default rule to an ethics obligation will silently conclude the document is out of date.

  **Generalise, but gate admission on implementation ramification.** The generic treatment is what stops five bespoke mechanisms (ethics, DMP, licensing, classification, accessibility mandate), and ethics is the exemplar that earns the work rather than a special case to be diluted. The risk of the abstraction is a drawer of value statements — "we care about participant privacy" — which cost context and constrain nothing. The admission test is concrete: **can this be violated by a line of code, a schema, or a deployment choice?** If not, it is not this. Naming is open (*principle* invites the bumper sticker; *obligation* is accurate but reads narrower than the intent), and the naming should follow the test rather than the other way round.

  **Provisionality is the mechanism, not a caveat.** Work routinely begins before approval, so an obligation has a lifecycle — anticipated (institutional policy, typical HREC conditions, the brushstrokes known at the start) → submitted → in force → amended — and design done against an anticipated obligation may need revisiting when the approved text differs. The failure to prevent is an anticipated obligation read as one in force: the constitution's *descriptive claim in a normative register* failure, one level up, and `## Not yet in force` is the existing precedent for the split. The state has to be visible at the point of load, because it decides whether the agent treats the constraint as a hard boundary or a working assumption.

  **The audit is the part that can do harm.** `/b-review` is module-scoped and reviews code against plans; a principles pass is project-scoped and asks, for each in-force obligation, what discharges it and whether anything contradicts it. But `framework-reference.md` states plainly that *coverage is opportunistic, not an audit*, and this would claim precisely what the framework has so far declined to claim — with a compliance flavour that invites reliance. In an RSE setting the plausible misuse is real: a report headed "ethics conformance" could end up cited in an annual report to a human research ethics committee. Whatever ships must produce **evidence and gaps for a human reviewer**, must never emit an attestation, and must say what it did not look at. Over-claiming here is worse than not shipping.

  **Candidate shape.** The ADR machinery is the right *machinery* and the wrong *semantics*: a sibling register (`docs/principles/` or similar) with ADR-like frontmatter — stable ID, source, lifecycle state, `scope`/`modules`/`topics` classification so relevant obligations load at `/b-feature` propose time exactly as ADRs do — with the body carrying the obligation verbatim plus its implementation ramifications, and a generated index. The link that makes an audit possible is bidirectional: an ADR cites the obligation it responds to; an obligation lists the decisions and code that discharge it. An in-force obligation with nothing discharging it is then the finding.

  **Known traps, so they are not re-derived:**

  - **The discharge link is a derived-state axis with no derivation** — the same objection that defers *An implementation state for ADRs* below, and the same failure if unaddressed: a field maintained by hand, silently wrong, becoming the rotting second copy. Weigh the two items together; if one gets a workable answer, so does the other.
  - **The raw application may not belong in the repository.** Ethics applications can contain participant-identifying material, unpublished instruments, or third-party text, and repositories get shared and published. Extract the obligations; point at the protocol where it actually lives.
  - **Verbatim matters for the obligation text, and a paraphrase is a compliance risk** — but a scanned PDF is not loadable context. Something has to hold the operative wording, quoted, with provenance, and the extraction step is where an agent will most plausibly get it subtly wrong. Treat extraction as gated human-reviewed work, not a convenience.
  - **Amendment is the common case, not an edge case.** Protocols get amended mid-project, and an amendment can invalidate design already built. ADR immutability plus supersession is the closest existing pattern and probably transfers; what does not transfer is the assumption that supersession is initiated from inside the project.
  - **Cost check before building:** a new document class touches the viewer's schema contract, `/b-index`'s derivation, `/b-spec`'s export, and plausibly `/b-design` Stage 2 and the analyst's brief; an audit is either a fourteenth command or a `/b-review` dimension on a command that is currently module-scoped. This is a large item — sized like the review lifecycle, not like a marker change.

  *Revisit trigger:* the first real project whose design is constrained by an approved protocol — that project supplies the obligation text, the anticipated-versus-approved delta, and an honest answer on whether the discharge link is maintainable. Sooner if a project puts ethics obligations in `constitution.md` and an agent treats a received constraint as a project-amendable rule, which is the specific failure this item predicts. Do not build it from imagined protocols; the schema will be wrong in ways only real text reveals.

- **Opaque agent memory is a second home for project state, and Bower should call it a defect** — *Found at v0.33 while investigating a cross-runtime `b-recap` divergence on a real project.* Claude Code carries persistent memory at project and user level; Codex has neither, and OpenAI's guidance is instead **file-based memory** — state in the repository, reachable by any session. That guidance and Bower's *state has one home* are the same principle, which inverts the obvious reading: the runtime without opaque memory is the conformant one, and opaque memory is the defect surface.

  The case against it is Bower's existing case, applied to a store the framework never considered. A memory record holding project state is **not in git, carries no schema, is invisible to the viewer, is unreachable by `/b-review`, and does not survive a change of runtime**. None of the ownership norms that keep `constitution.md` honest reach it — there is no flag-don't-fix duty on a memory entry, nothing derives from it, and nothing ever contradicts it. Observed in one project's memory: a doc-link convention, a framework defect plus the decision to leave the project unswept as its test bed, a preference for canonical framework shapes, and — the sharpest instance — an entry asserting that a particular document is **non-authoritative**. That last is authority itself living outside the repository.

  **Point the rule at the repository, not at memory.** Bower has no business legislating a store it cannot read on every runtime, and "here is what may go in memory" invites a taxonomy nobody can settle. The rule that works is one-directional:

  > Every fact required to work on this project is in the repository. An agent may hold facts about the operator and their environment wherever its runtime provides; it may hold nothing about the project there.

  And it comes with a test, which is what actually decides cases: **would a fresh session, on any runtime, on a clean clone, with no memory, get this right?** If not, it was project state and belongs in the repo. Delete the entry and see whether project work degrades.

  **The residual class is exactly two kinds**, and neither is a grudging exception — the repository actively should not hold them. *Facts about the operator* (what they are unfamiliar with, how they prefer to be addressed): not normative, about a person rather than a system, volatile, and a repo is shared — a versioned file recording what a named person does not know is readable by collaborators and anyone else with access. *Facts about one machine* (an MCP that fails on this WSL box, where a cached binary lives): making these project rules is the exact failure `framework-reference.md` already forbids — a descriptive claim in the register of a rule, false for the next contributor on another platform.

  Both are *not project state*, which means the symmetry objection dissolves: they never needed to be in the **project**, so a user-level file outside the repo serves both runtimes equally and no per-runtime split arises. Do not argue this on efficiency — memory being slower to search is true and not load-bearing, and someone will rebut it with "memory got faster". The objection is a category error in both directions.

  **A third class has no residual claim either: in-flight work state across sessions.** Not a decision, not a convention, not about the operator — just where a multi-session task got to. Bower already homes this in `status.md`, `plan.md`, `review-plan.md` and the adoption ledger, and in this repo in `docs/conformance/runs.md`. Instance: the v0.33 C3 run's state lived in a memory entry plus an out-of-repo resume file, and reorienting a later session required reading both to discover what had been decided about a tier claim *inside* the repo. That is the cost the one-home rule predicts, paid by the framework's own workflow.

  **Where it lands:** the substance in `_bower/framework-reference.md` under *Document Layers and Ownership*, which already carries the ownership semantics this extends; one tight line in `_bower/framework.md`, since it binds every session. Phrased as a rule about the repository it names no tool and no mechanic, so it stays out of *Runtime bindings* and **does not trigger the demotion rule**. The migration is judgement-class and genuinely useful: audit the project's agent memory, promote project facts into `docs/`, delete them rather than duplicating them. Still open: whether the audit gets a recurring home (a `/b-review` dimension, a `/b-recap` line, its own command) or is a one-time migration.

  **Notes for whoever picks this up**, so the reasoning is not re-derived:

  - **The migration is a research instrument, not a chore.** Run it against a real accumulated store — Lyrebird's is the candidate, ~16 entries — and its output is a *classification*, including an explicit **unclassifiable** bucket. If everything sorts into the three kinds above, the taxonomy holds; if several resist, the two-kind residual class is wrong and the guidance should say something else. Design the note to report before it acts.
  - **Four dispositions, not two.** Promote (with the named Bower home) · keep (operator or machine fact) · **delete as obsolete** · unclassifiable-report. The third is load-bearing: without it the audit dutifully promotes stale facts into `docs/`, which is the same defect in a new place.
  - **Memory is unversioned and deletion is irreversible** — the only Bower operation with no git safety net. Snapshot the store before any run, and gate the dispositions as a **batch gate** (the idiom already exists), never one omnibus approval.
  - **The auditing agent wrote the entries it is judging**, which is a real conflict — it may keep what it chose to record, or over-promote to look thorough. The gate has to be genuine rather than a formality.
  - **Do not name a memory path in the framework.** A concrete store is a runtime mechanic, which would put this in *Runtime bindings* and trigger the demotion rule for a rule that has nothing to do with gates. Have the note ask the agent to report whatever store it can see, and to declare the step a **no-op** where it has none.
  - **Evaluate disabling the runtime's memory outright.** Claude Code's memory can be turned off, which is worth assessing for two different purposes. As a **conformance control** it is better than the fresh-path workaround recorded above: a fresh path loses the real project and still accumulates memory during the run, whereas disabling gives a fair cross-runtime comparison *on real data*. As a **project posture** it is stronger than any guideline — it converts an unenforceable rule into configuration, the same move as excluding `docs/` from the formatter rather than asking each agent not to run it. If the lever is a setting, `_bower/project-settings.json` already seeds `.claude/settings.json`, so the scaffold could carry it; **verify the actual mechanism before designing around it** rather than assuming a settings key exists. Two honest costs to weigh: it discards the legitimate residual class (operator and machine facts) unless those get a user-level home first, and a framework that ships a runtime-specific setting has put a runtime mechanic in the scaffold, which needs thinking about against the *Runtime bindings* containment rule even though a config template is not instruction text.
  - **Detection posture, tentatively opportunistic** — no new command, no `/b-review` dimension, no `/b-recap` surface: nothing can enumerate memory on every runtime, so a promised sweep is a claim the framework cannot keep, and the constitution's *coverage is opportunistic, not an audit* caveat is the precedent. Not settled; the alternative is a dedicated command, which buys a re-runnable classification report at the cost of a fourteenth surface.

  *Revisit trigger:* scheduled for v0.35 alongside the conformance rethink, whose memory control (disclose the memory, or run the Claude side from a fresh path) is this finding's cheap half. (It was stamped v0.34 until the findings/review strand took that version.) Sooner if a decision existing only in memory causes a fresh session or the other runtime to act against it.

- **A delegated role's elapsed time is not evidence of failure, and an interrupted report is not marked as one** — *Found on a real project at v0.33, on the first delegated `/b-feature` implementation run under Codex. Deferred at v0.33 because the fix edits `Runtime bindings` → Delegation, which triggers the demotion rule; see the cost note below.* Two halves, and the second is the one that matters.

  **The mechanic.** `Runtime bindings` → *Delegation* says "wait for its structured artifact" and stops there. Under Codex the wait primitive returns a timeout for an expired **polling window**, which reads as a hung subagent; the caller sent an interrupt after several polls on elapsed time alone, against an implementer legitimately running a project's full test suite. The binding needs a clause: a polling timeout is not a failure signal, keep waiting and report progress to the operator, request status without interrupting if reassurance is needed, and interrupt only on concrete evidence of a stall. Project-specific expectations ("the backend suite takes two minutes") do **not** belong in the delegated packet — that is what the constitution's testing section is for, and the implementer already reads it.

  **The provenance.** There is no marker for a report produced under interrupt. The caller reconciles `status.md` and the acceptance mapping *from the report*, and an interrupted report describes a run that did not finish while looking identical to one that did. In the observed run the subagent reported 982 passing under interrupt and the caller's own re-run found 983; which of "a test was added between the two" and "the report described an unfinished run" was true **was never established**, and the framework gave nobody a reason to ask. This is structurally the `Context: inline` problem — a degradation that must be announced rather than slid past — and the natural shape is the same marker discipline: written by the caller, into the artifact, naming what was degraded. It touches the implementation-report shape, so the viewer's schema contract needs checking before it moves.

  A third observation belongs with these: after interrupting, the caller re-ran the full suite **on its own thread**, which defeats the entire reason implementation is delegated — keeping a large test-output context off the orchestrator. Whatever the fix, it must not prescribe re-verification on the caller's thread.

  *Cost note:* the first half edits `Runtime bindings`, so the demotion rule applies — C3 on both runtimes, C8 on Codex, before the version repeats a tier claim. Do both halves in the same version so that re-run is paid once.
  *Revisit trigger:* the next version that touches gate or delegation text for any other reason, since the demotion cost is then already being paid. Sooner if a second delegated run is interrupted on duration alone, or if any project reconciles an interrupted report's acceptance mapping into `docs/` as though it were complete — that is the failure this defers, and it is silent.

- **A stored `## Next move` has no retirement path when a feature can never reach `✓`** — *v0.33 fixed `/b-recap`'s half of this: the recommendation is derived and pending-verification features are excluded from the continue-in-progress rung. The stale line itself was left in place.* v0.30 made a stored `Next move:` feature-scoped and retired it at `✓`. A feature awaiting manual verification is pinned at `🚧` by `framework-reference.md` until a human acts **outside the repository** — a dashboard change, a deployment check, a device test — so `✓` may be months away or never come, and the stored line survives indefinitely. Observed on a real project: `cloudflare-config/status.md` carried `Run /b-feature cloudflare-config`, written by the run that parked it, pointing at itself. `/b-feature` on such a feature finds nothing to build and writes the same line back, so the loop is stable rather than self-correcting.

  Why it was not fixed with the rest: the candidate shapes all touch what `status.md` *is*, not just how a command reads it. A `Next move:` that names the operator's action instead of a command changes the field's meaning from "what to run" to "what happens next", and both the viewer's schema contract and `/b-index`'s derivation would need checking. A second terminal form alongside the `✓` one — pinned-pending-operator — is a marker-vocabulary change with reach into `module-status.md` and the integration floor. Suppressing the line at write time in `/b-feature` is the cheap option and the least honest, since the state is real and worth recording. Picking among these needs the schema question settled, which is more than a release-eve fix.
  *Revisit trigger:* a second feature parked on an out-of-repo check, or any project where a stale stored next move misdirects a run *after* v0.33's `/b-recap` fix — the fix stops recap repeating it, and does nothing about `/b-feature` being invoked on it directly. Also worth bundling into any change that touches `status.md`'s schema for another reason.

- **Rework what `docs/index.md` is allowed to be** — *v0.28 closed the ratchet: status prose is derived by definition however it is worded, curated sections carry a budget and an overflow report, and the four commands that offered a free-text index write no longer do. What remains open is the structural question: whether an index of this shape should exist at all, given that everything in it is either derived from somewhere else or a pointer to it.* An index is **read in full, every session, by every command**, which makes its size a standing tax rather than a cost paid on opening. Preserve-don't-flatten is right for accuracy, and on its own it leaves curated sections with **no wholesale writer, therefore no budget, therefore only growth** — the budget and overflow report are a floor under that, not an answer to it. Observed on a real project: a hand-grown `## Status overview` table whose `Stage` cell had reached ~15kB of narrative covering every module's state, in a file nothing read back.

  The size was the symptom. The defect is the shape: **narrative in a table cell cannot be surgically edited.** There is no heading to anchor to, no section an agent can target, and no writer that rebuilds it — so the only available edit is rewriting the whole paragraph between the pipes, which is why in practice it gets appended to and never compacted. It also duplicates what `module-status.md` and `architecture.md` already say, with nothing keeping the copy honest — *State Has One Home*, failing on an axis the rule was not written for.

  The open question is whether `derived` vs `curated` is the right split at all, given that "curated" has come to mean "unbounded and unmaintainable." Candidate shapes: a stated budget for curated index sections that `/b-index` reports on rather than enforces; a rule that an index may only *point*, never summarise, so status prose has no home there; a bounded schema for the overview section (fixed keys, short values) that `/b-index` owns as derived state rather than preserves as curated; or accepting narrative but requiring it in headed prose sections rather than table cells, so it is at least addressable. v0.28 took the cheap half — guidance in `framework-reference.md` under *Document Layers and Ownership*, and an `oversized-table-cell` check in the viewer so the condition is visible rather than silent.
  *Revisit trigger:* the next time a project's `index.md` needs surgical editing and cannot get it, or a second project grows an unbounded curated section. Also worth doing proactively if `/b-index` is being changed for another reason — the rework is cheapest bundled with work already in that file.

- **Docs-viewer drift checks wired into `/b-review` (or `/b-recap`)** — *Viewer shipped human-facing in v0.28.* `_bower/viewer/lib/extract.cjs` already computes ~two dozen mechanical drift findings that overlap `bower-reviewer`'s *spec↔code drift* and *status honesty* dimensions: marker disagreements, a `✓` over pending verification, one-sided ADR supersession or narrowing pairs, plan `Components` files that are not on disk, stale `Delivered by:` pointers. A reviewer that shelled the extractor would get those for free and could spend its own reasoning on what a parser cannot see. The natural shape is **graceful enhancement**, same posture as the interface-observation item below: use it when `node` is present, fall back to today's behaviour otherwise. Deliberately not done in v0.28 for two reasons. First, it makes the extractor's output a *contract* — findings would gain the weight of review items, so the kind names, severities and message shapes could no longer be changed freely, which is exactly the freedom a tool this young needs. Second, Bower's agents read `docs/` directly by design, and a second orientation source that can disagree with the documents is the failure mode `/b-index` and `scope.md` were both restructured to avoid; a mechanical pre-pass would need a clear rule for which wins. Keeping the viewer a reading surface for the human costs nothing and forecloses nothing.
  *Revisit trigger:* a `/b-review` run whose report misses a finding the viewer's drift page had been showing, or two reviews in a row whose owned-drift items are all things the extractor already computes. Either says the reviewer is doing by hand what a parser does exactly.

- **VS Code extension shell over the viewer's extractor** — `extract.cjs` and `web/` are shell-agnostic on purpose: the client reaches its container through one narrow `HOST` interface (`openFile`, `graphUrl`, `eventsUrl`), so an extension swaps three functions and reuses every view. The pieces an editor integration wants are already in the graph — reverse file → owning-feature lookup, per-file ADR context, the drift checks as live diagnostics in the Problems panel — so this is a new shell, not new extraction. Deferred because the browser shell covers the actual observed need (read the state, spot drift) and an extension adds a packaging, publishing and VS Code API-version maintenance burden the framework does not otherwise carry.
  *Revisit trigger:* the file → feature lookup or the drift checks are wanted *while editing a specific file* often enough that switching to a browser tab is the friction. Wanting the module graph is not that signal; wanting drift on the file under the cursor is.

- **`/b-adopt` real-project validation and v2** — *v1 shipped in v0.21.* `/b-adopt` reconstructs an orienting `docs/` skeleton from an existing codebase and, when unattributed choices remain, opens an adoption phase (banner in `index.md` + monotonically-shrinking `docs/adoption-ledger.md`, drained by resolve→ADR / remediate→`/b-feature`|`/b-design` / dismiss→delete). Deliberately bounded for v1: the repo survey uses the generic `general-purpose`/`Explore` agent rather than a bespoke `bower-surveyor`; `/b-feature` is *not* rewired to consult the ledger when working in an area (the always-read banner plus manual drain is judged enough for a first trial); dismiss leaves no tombstone. Candidate v2 work, all gated on the first real run: a dedicated survey agent if context economy or inventory quality demands it; ledger-aware orientation in `/b-feature`/`/b-module` during the adoption phase; whether module-boundary inference is good enough or needs a heavier interactive pass; whether reusing `🚧` for as-built/unverified features is clear enough in practice or a dedicated adoption marker earns its framework-wide cost (v1 reuses `🚧` deliberately to avoid taxing the status vocabulary). The adoption-aware `/b-review` fallback that was listed here is now its own item below, having grown a stronger case than the rest of this list.
  *Revisit trigger:* the first real brownfield adoption is run and reported back on — what the reconstructed docs got wrong, whether the ledger drained cleanly through normal work, and where the operator wished for more automation.

- **Adoption-aware `/b-review`** — *Split out of the `/b-adopt` v2 item in v0.29, because the case for it is now judged strong rather than speculative: review is the natural pass for turning as-built code into recorded decisions, which is exactly what an adopted project is missing.* Today `/b-adopt` forbids it, and correctly — `bower-reviewer` reads each feature's `plan.md` and `status.md` in full and uses the plans to locate code, and adoption deliberately creates neither. Making it work is a reviewer redesign, not a relaxation of the prohibition, because the six dimensions do not survive the missing files intact. Four hold up on an adopted module: **test coverage** (tests and code are both real), **cross-feature consistency**, **boundary integrity** (`architecture.md` exists post-adopt), and **ADR drift** — though the last mostly reduces to the *absence* of ADRs, which is the adoption ledger's job rather than a review finding. Two are meaningless: **spec↔code drift** has no spec to drift from, and **status honesty** has no `status.md` and every marker is `🚧` by construction. So the work is: a reviewer mode that tolerates missing per-feature files, locates code without a `## Components` table, runs the four surviving dimensions and says which it stood down; findings that will be nearly all `route:/b-feature` (which is also the ledger-drain path, so the two need a story about overlap); and rewriting `b-adopt.md`'s two prohibitions rather than deleting them. The v0.29 review-state work is compatible with all of it — an adopted module carries `Review: ⏸` and the schema nowhere requires per-feature files.
  *Revisit trigger:* wanted on a real adopted project — the operator reaches the end of an adoption and wants a review pass over a module rather than a feature-by-feature `/b-feature` walk. Bundle with `/b-adopt` v2 if that lands first, since both touch the same prohibitions.

- **An implementation state for ADRs** — *Raised by a real v0.31 review whose `route:/b-design` finding was discharged by an accepted ADR while the boundary erosion stayed in the code; v0.32 fixed that case inside `/b-review` (discharge is verified against the code, and a design decision whose implementation has not landed re-classes to `route:/b-feature`), but only that case.* The general problem is that **an accepted ADR is a commitment and nothing asks whether it was built.** `/b-design` normally emits work as build-order entries, so `/b-index` tracks it — but a decision that reshapes an existing component adds no features, carries no roster entry, and is then scheduled by nothing. *Code is truth, ADR is hypothesis* cuts unhelpfully here: an unimplemented accepted ADR is precisely a stale hypothesis, and no command looks for one. The candidate shape is a **mutable frontmatter field** (`implemented: true | false | n/a`), which fits the schema exactly — ADR frontmatter is already mutable while bodies are not, the same property `supersedes`/`narrows` rely on — with `/b-index` surfacing accepted-but-unimplemented ADRs and `/b-recap` reporting them. Deferred because the cost is a **new derived-state axis with no derivation**: nothing computes it, so it is maintained by hand or not at all, and a field that silently stays `false` forever is the rotting second copy the framework spends most of its rules avoiding. `n/a` is also a large and ill-defined category — many ADRs are pure convention with nothing to build — and a tri-state whose most common value means "ignore me" is weak signal. v0.32's narrower fix costs nothing and forecloses nothing.
  *Revisit trigger:* design output is orphaned **outside** a review — an accepted ADR is found unimplemented by some path other than `/b-review`'s verification, or an operator asks "which of our ADRs are actually built?" and there is no way to answer. One instance inside a review is already handled; the trigger is specifically the case v0.32 cannot see.

- **Review-staleness snapshot: diagnosis-time vs closeout-time** — v0.29 writes the `(N of N features)` roster snapshot from the count taken at *diagnosis*, so a review whose routed `/b-feature` work itself added features reads as slightly stale the moment it closes. That is honest — those features genuinely were not reviewed — but it may prove annoying enough to be noise, in which case the alternative is snapshotting at closeout, which trades honesty for a quieter signal. Not decided on first principles because the frequency is unknown: it needs real reviews with real routed work to say whether the case is common or a curiosity.
  *Revisit trigger:* a review closes stale-on-arrival and the operator finds the staleness note unhelpful rather than informative, twice. One instance is the design working as intended; twice says the default is wrong.

- **Codex from experimental to supported** — *v0.33 shipped the dual-runtime delivery and earned the experimental tier: a clean scaffold install plus the C3 core gate holding under an explicit trust waiver, on the weakest supported model. The residual is evidence, not design.* Graduation needs every scenario in `docs/conformance/` green — PASS or PASS-WITH-DEGRADATION with each degradation named in its scenario file — and a gate-refusal FAIL blocks it outright. Outstanding at v0.33: C2, C4, C5, C8 and C7 under `danger-full-access` on the Codex side (all operator-interactive, which is why they were not run unattended), and the C1–C5 regression baseline on Claude Code. Two open observations to settle while running them: whether the parent sandbox mode gates delegation (C6 fell back to inline under `read-only` while C1/C7 spawned real threads under `workspace-write`, but model and effort are confounded across those three runs), and whether the missing `cancel` choice seen once at a feature gate is variance or a wording defect.
  *Revisit trigger:* a green row set in `docs/conformance/runs.md` covering C1–C8. Partial progress is worth recording as it happens — the ledger is append-only and a FAIL row is more useful than a missing one — but the tier claim moves only when the set is complete.

- **Runtime delivery beyond the checked-in pair** — Two separable questions the v0.33 work deliberately left alone. **Plugin distribution:** Codex plugins can package skills and MCP tools, but they need separate installation and a new session, are absent from some Codex surfaces including the IDE extension, and the official guidance points repo-scoped workflows at `.agents/skills/` — which is what Bower ships. A plugin would be a discovery aid on top of the checked-in footprint, never a replacement for it. **Further runtimes:** the generator makes a third adapter tree cheap to emit (one transformation function, one lint), and the conformance suite makes the *claim* expensive — which is the right ratio. Any new runtime enters through the same door: name the primitives it cannot provide, generate rather than translate, and earn a tier.
  *Revisit trigger:* for plugins, an operator who cannot use the checked-in footprint — a Codex surface that does not scan `.agents/skills/`, or a team wanting Bower without a repo commit. For a third runtime, someone able to run it end-to-end and willing to score it against the existing scenarios; installation plus one gated write workflow is still the minimum evidence for *experimental*.

- **Interface-observation tooling wired into `/b-ui`** — Integrate an observation tool (e.g. `chrome-devtools-mcp` for web, equivalent harnesses for TUI/desktop) into `/b-ui` Step 4 as **graceful enhancement**: when an observation tool is available in the session, take a screenshot (or capture equivalent state — DOM dump for web, terminal capture for TUI, window state for desktop) *before* the PENDING USER manual-check question, so the user sees "here's what it looks like, confirm or tell me what's off" instead of being asked to go check themselves. Sessions without the tool fall back to today's behaviour — no hard dependency, no required setup. Same posture as the rest of Bower: opinionated about shape, light about prerequisites. Includes documenting the WSL2 headless setup for web tooling, since that's where most adopters will hit setup friction first. Scope discipline: this is the screenshot-before-confirm hook only; ongoing test-harness enforcement of `ui.md` invariants is the next item.
  *Revisit trigger:* two or more real `/b-ui` (or path-2 ad-hoc) cycles in a project where the manual-check round-trip produces back-and-forth that a screenshot would have prevented. The pain should be felt before the dependency is added — the integration is cheap enough that it doesn't earn pre-emptive work.

- **Living invariants for `ui.md` via test harness** — Treat invariants written in `docs/ui.md` ("destructive actions are undoable for 5s", "modals trap focus", "navigation persists in URL", "ESC closes overlays") as testable contracts and wire a test runner to assert them: Playwright for web, Textual's pytest support for TUIs, native test harnesses for desktop. Today invariants are written but not enforced — they sit in the doc as commitments that can drift silently from code. Project-specific by nature: different surfaces need different harnesses, and not every project will want the overhead. Likely lives in `constitution.md` conventions plus an optional pattern in `module-status.md` for which features carry interaction-pattern tests, rather than as a framework default. Distinct from the screenshot-before-confirm item above: that's verification *at acceptance time*; this is *ongoing enforcement* between commits.
  *Revisit trigger:* a project actually writes invariants in `ui.md` that drift from code, and the drift is caught only at manual review (or worse, by a user). Until that pain surfaces, the test-harness investment isn't worth its overhead.

- **Retirement lifecycle and `♻️` marker** — A convention for what happens to features that are removed or abandoned (keep `plan.md` as historical record, move under `modules/<m>/retired/`).

- **`architecture.md` splitting for scale** — Keep `architecture.md` as a short overview; push component-level detail into module-scoped architecture docs. - **Single source of truth for duplicated schemas** — Schema text still appears in more than one place (e.g. the ADR schema in `/b-adr`, `framework-reference.md`, and `docs/adr/index.md`). Acceptable duplication for now, since each copy serves a distinct load path, but it can drift silently. The fix is to nominate one canonical copy per schema and generate or `@`-include the rest. (The broader CLAUDE.md tiering this was bundled with was realised in v0.20 — see `changes.md` — and is no longer roadmap work.)
  *Revisit trigger:* a schema change that has to be applied in three places and one is missed. **Nearly fired in v0.27** — adding `narrows`/`narrowed-by` to the ADR schema required edits to `framework-reference.md`, `/b-adr`, and `/b-index`'s seed, plus a migration step for each project's already-written `docs/adr/index.md` schema block (which `/b-index` treats as curated and will not overwrite). Nothing was missed, but the fourth copy is only reachable by migration note, which is the weakest of the four paths. Canonicalisation was deliberately not bundled into v0.27: it changes how schema text is *delivered* (generation or `@`-include) and would have made a schema addition and a load-path change reviewable only together.

- **Constitution template and archive rules** — A schema for `constitution.md` and explicit rules for what belongs in `_bower/archive/`.
  *Trigger fired (constitution half), v0.23:* a real project's `constitution.md` asserted that something existed when it was an aspiration, and agents downstream treated it as fact. v0.23 adds the **normative shape rule** — the constitution states rules, not descriptions; claims about what exists must be verifiable or live under `## Not yet in force` — plus flag-don't-fix reporting from `bower-implementer` and `bower-reviewer` and a consent gate in `/b-feature` and `/b-review`. This is deliberately a *shape* rule, not the full template the item envisaged: headings beyond the aspiration split stay the project's own business, since no failure has yet argued for prescribing them.
  *Still deferred:* the full heading schema, and the `_bower/archive/` rules (untouched by v0.23).
  *Revisit trigger:* a project's `constitution.md` drifts into an ad-hoc shape that the normative/aspirational split alone did not prevent, or `_bower/archive/` contents become ambiguous about what belongs there.

- **Durable-ephemeral proposals on disk** — `docs/proposals/<slug>.md` written at the gate, deleted on completion, to survive session boundaries.
  *Revisit trigger:* if session-boundary pain shows up after first real use.
  *Partially realised (v0.18):* `/b-review` instantiates this pattern for the review use-case — `docs/modules/<module>/review-plan.md` is written at the triage gate and deleted on completion, surviving a mid-apply crash. v0.34 adds a second instance, `docs/modules/<module>/findings.md`, which is the same durable-ephemeral shape with the state machine removed entirely: appended by any command at a gate, drained by whoever discharges the items, deleted when empty. Two instances with different owners is now some evidence about what the general convention would have to accommodate. The *general* convention (a `docs/proposals/` home for any gated, multi-step change) is still deferred.

- **Extend the implementation-agent boundary to `/b-module`** — v0.20 delegates `/b-feature`'s post-gate implementation to the `bower-implementer` subagent; `/b-module` still implements inline and suffers the same (worse — N features per session) context accumulation. - **Slim `docs/index.md` and `module-status.md` back into routers; separate `integration-plan.md`** — Observed in a mature project: `docs/index.md` grows a rolling project narrative repeating plans, UI docs, ADRs, and module status; a module-integration note grows into a detailed future end-to-end specification. Cost is modest but grows linearly with project maturity and taxes every feature invocation. The shape: `docs/index.md` stays at module marker / current feature / next feature / blockers; `module-status.md` at build order, boundary invariant, integration-state pointer; detailed cross-feature integration obligations move to a `docs/modules/<module>/integration-plan.md` loaded mainly by `/b-integration`; feature detail stays in feature plans. Shares territory with the *`architecture.md` splitting for scale* item above — both push detail out of a growing top-level doc into module scope; weigh doing them together.
  *Revisit trigger:* a project's index or module-status narrative measurably taxing feature invocations again after v0.20's selective orientation lands — the selective reads may already blunt the cost enough.

- **Migrations as per-version files, repo-side** — Replace the single changelog with `docs/migrations/index.md` (the version index — version, date, one-line summary, migration class) plus one file per version, all in the framework repo and none of it scaffolded. Retires the line-number bookkeeping v0.25 added to `/b-upgrade`: a step reads one whole small file instead of computing a range between headings. Two consequences to weigh when picking it up — `_bower/changes.md` could leave the scaffold footprint entirely (nothing in a project reads it; `/b-upgrade` clones), and `scripts/release.sh` gets simpler (cat a file rather than extract a section). Open question is which columns the index needs to stay small while being the only file that grows.
  *Revisit trigger:* a 1.0 release, when the framework shape is stable and the v0.25 index format has enough versions behind it to show whether its four columns are the right ones. The pre-1.0 posture — rapid churn, heavy migrations, only a limited version range tracked, cut at substantial architectural splits — is what makes the current single-file-plus-archive shape sufficient until then.

- **Token optimisation pass** - A pass through all framework instructions to tighten up the language reduce the token count as a speed and cost optimisation. Overall framework token use is still on the light side compared to many frameworks, and there is no active harm on the overly verbose instructions. Implementing this requires a definition of "token optimisation" which is a mini research project in itself.
  *Research done — see [`docs/context_optimisation_report.md`](../docs/context_optimisation_report.md).* Assesses Bower against Anthropic's *New Rules of Context Engineering for Claude 5 Generation Models* and supplies the missing definition — but a different one than this item assumed: the criterion is *remove instructions that compensate for model limitations, and let interfaces carry what prose duplicates*, not *tighten prose to cut tokens*. The report records a **tuned-for-Opus-5 stance** — held through v0.33's dual-runtime landing, since that work removed no contracts, but now with a second reader to weigh: the conformance runs are deliberately scored on the weakest supported model, so an instruction this pass would cut as redundant for Opus 5 may be the one holding a gate on that floor. Any tranche picked up from here re-runs C3 and C8 under the demotion rule, finds the `<critical_constraints>` restatement blocks across twelve of thirteen commands to be the main misalignment, and proposes three separable tranches with near-zero project-side migration cost. When picked up, rewrite this item to the report's framing rather than executing it as originally worded.
